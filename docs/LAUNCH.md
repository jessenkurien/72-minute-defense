# Launch checklist

This file is for the maintainer. Keep it, move it to an issue, or delete it before the first release.

## Before publishing

1. Review your employment agreement, IP-assignment terms, and moonlighting policy. Use only personal accounts, personal time, synthetic data, and systems you are authorized to test.
2. Keep the public `Example Corp` policy as a fictional, unarmable template. Do **not** replace the fictional CISO or VP attestations with your own name; one person should not claim three organizational roles.
3. Run the complete verification set:

   ```bash
   ruff format --check .
   ruff check .
   pytest -q --cov=seventytwo --cov-report=term-missing --cov-fail-under=85
   72md policy verify
   72md rehearse --out out --audit out/audit.jsonl --fail-if-late
   72md audit verify --audit out/audit.jsonl
   ```

4. Confirm the README test count, coverage, and four scenario results still match the output.
5. Confirm README, NOTICE, LICENSE, SECURITY, and `pyproject.toml` contain no placeholder identity or contact details.
6. Create a public GitHub repository named `72-minute-defense`. Suggested description: `Reference implementation for governed, pre-authorized ransomware containment measured against a 72-minute exfiltration benchmark.`
7. Upload [`social-preview.png`](social-preview.png) in **Settings → General → Social preview**. Confirm GitHub shows **Cite this repository** from `CITATION.cff`.
8. Suggested topics: `ransomware`, `incident-response`, `ransomware-containment`, `incident-command`, `policy-as-code`, `security-automation`, `security-orchestration`, `itdr`, `soar`, `xdr`, `ciso`, `grc`, `nist-csf`, `security-leadership`, `tabletop-exercise`.
9. Push, confirm CI and the policy gate are green, then enable branch protection, Dependabot alerts, secret scanning, and private vulnerability reporting.
10. Create release `v0.1.0` only after the checks pass from a clean clone. Attach the source archives generated by GitHub; do not upload local environments, credentials, audit logs, or rehearsal output containing organizational data.

## Important language for demos and interviews

Say:

- “This is a reference implementation and governance pattern.”
- “The four numbers are synthetic, deterministic rehearsal outputs.”
- “The public template is deliberately blocked from live execution.”
- “Digest attestations make policy edits visible; protected review authenticates the approvers.”
- “All adapters are mock or stub tested and still require tenant validation.”
- “The audit chain detects interior modification; production completeness requires external anchoring.”

Do not say:

- “Production-ready” or “enterprise-ready.”
- “Cryptographically signed by executives.”
- “Every action is automatically reversible.”
- “The exact API request” when a live call requires runtime discovery.
- “Compliant with” NIST, ISO 27001, SOC 2, GDPR, or another framework.
- “Proven time to contain” without real alert, approval, platform, and recovery measurements.

## Suggested LinkedIn post

The 72-minute number is not a prediction for every incident. It is a leadership deadline.

Unit 42's 2026 research reports 72 minutes as the quickest-quartile time from compromise to data exfiltration. Most security tools already know how to revoke a session or isolate a host. The difficult question is whether the organization has decided — before 2 a.m. — who may do it, against what assets, within what blast radius, and with what review.

I built an open-source reference implementation called **The 72-Minute Defense** to explore that decision.

It includes:

- A four-tier containment authority policy with protected assets, ceilings, approvers, accepted-impact statements, and digest-bound attestations.
- An ATT&CK-aligned precursor-chain scorer and business-context-aware decision engine.
- One operating rule: do what is pre-authorized now; escalate the rest.
- Dry-run adapters for Entra, Defender, Okta, CrowdStrike, and AWS.
- A hash-chained decision and action log, with its limitations documented.
- Four synthetic rehearsals and a CI policy gate.
- A GRC discussion pack covering NIST CSF 2.0, ISO/IEC 27001, SOC 2, GDPR, RACI, risk treatment, tabletop exercises, and staged delivery.

The current synthetic scenarios contain at minutes 19, 28, and 32. A lone CEO login anomaly correctly causes no containment action. Those are repeatable outputs from the included scenarios — not claims about a production environment.

The most important design lesson was that a higher-impact action waiting for approval must not block a lower, already-authorized containment step. Governance should define safe speed, not accidentally remove it.

I would value feedback from incident commanders, SOC leaders, GRC teams, platform engineers, and auditors: **what evidence would you require before authorizing automatic containment in your environment?**
